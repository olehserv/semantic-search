## Чому такий порядок

1. **Phase 0 спершу** — відтворювані інсталяції і CI роблять кожну пізнішу зміну
   перевірюваною; виправлення C2 крихітне і прибирає найгірший досвід першого
   запуску.
2. **Phase 1 перед Phase 2** — налаштовувати якість безглуздо, поки кожен
   запит стартує ~30 с і жоден реальний агент не може викликати інструмент.
   Phase 1 також уже спроєктована і спланована; це чисте виконання.
3. **Phase 2 з контролем через оцінювання** — це власний задекларований метод
   проєкту ("зміна є покращенням лише тоді, коли це підтверджують метрики"), і
   середовище оцінювання вже існує.
4. **Phase 3 останньою** — більшість пунктів (безпечна перебудова, інкрементне
   індексування) мають значення лише після того, як існує архітектура сервісу
   з Phase 1.

## Поза обсягом (наразі)

- Мови, відмінні від .NET (але розбивач у 2.4 має тримати мову підключуваною).
- Автоматичне оновлення індексу всередині сервісу (стеження за файлами) —
  повернутися після 3.4.
- Endpoint `/ask` для LLM у сервісі — документ дизайну вже відхилив його
  (YAGNI).
- Масштабування понад один екземпляр сервісу (дизайн прогрітого singleton'а
  припускає одного воркера; нормально для внутрішнього командного інструменту).
