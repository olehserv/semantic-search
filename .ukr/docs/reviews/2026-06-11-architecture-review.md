# Огляд архітектури — Семантичний пошук по коду

**Дата:** 2026-06-11
**Рецензент:** Claude (огляд від старшого AI-архітектора/розробника, на запит Олега)
**Обсяг:** весь репозиторій на коміті `b4c8540` ("add evaluation")
**Подальші кроки:** C2/C4/H4/M5/M9 виправлено, а M11 здебільшого виправлено
роботою Phase 0 на гілці `phase-0-fixes` (того ж дня). Поточний статус дивіться
у `/handoff.md`.
**Результат:** Надійний прототип із дуже добрим середовищем для оцінювання. Але
він **не готовий до продакшену**. Головна можливість (доступ агента через MCP) не
працює зі справжніми MCP-клієнтами. Один підтверджений баг ламає перший запит на
свіжій машині. Затверджений редизайн (тривало працюючий сервіс пошуку) був
записаний, але так і не реалізований.

---

## 1. Що це за проєкт

Гібридний семантичний + пошук за ключовими словами по коду для кодових баз .NET:

```
build_index.py ──> Qdrant (vectors) + bm25.pkl (chunks)
query_index.py ──> vector(top6) + BM25 + vector(top12) → dedup → re-embed → weighted re-rank → JSON
ask.py         ──> found code chunks → local Ollama LLM → written answer
mcp_server.py  ──> stdin/stdout wrapper, starts query_index.py as a new process per request
eval/          ──> golden-set harness: Recall@k, MRR, nDCG@k (file level)
```

## 2. Сильні сторони (зберегти їх)

- **Середовище для оцінювання — найкраща частина репозиторію.** Чисті метричні
  функції без залежностей (`eval/metrics.py`), замінний `query_fn` для
  тестування, успішні юніт-тести, робоче наскрізне демо
  (`eval/run_demo.sh`), і README, який слушно зазначає: зміна є покращенням
  лише тоді, коли це підтверджують метрики. Це правильна основа для
  покрокового покращення кроку пошуку.
- **Чесні коментарі.** Код документує власні минулі баги (мертва перевірка
  replace у `build_index.py:53`, виправлення StorageContext у
  `build_index.py:86`, пастка з LLM за замовчуванням від OpenAI у
  `model_setup.py:19`).
- **Чисте розділення stdout/stderr** у `query_index.py:19` (усі логи йдуть до
  stderr, тож stdout лишається валідним JSON для машин).
- **Атомарний запис** для кешу ембедингів (`query_index.py:165-171`) — збій
  не може пошкодити файл кешу.
- **Існує справжній документ дизайну** для наступного кроку
  (`docs/superpowers/specs/2026-06-01-continuous-search-service-design.md`,
  статус "Approved") з відповідним покроковим планом. Дизайн хороший —
  його просто ніколи не реалізували.

## 3. Зауваження

Серйозність: **C** = критичне (щось зламано), **H** = високе (неправильні
результати або серйозний операційний ризик), **M** = середнє (якість /
зручність супроводу).

### Критичні

**C1 — `mcp_server.py` не є справжнім MCP-сервером.**
`scripts/mcp_server.py` використовує власний протокол: один JSON-об'єкт на рядок
(`{"tool": "search_codebase", "input": {...}}`). Справжній MCP — це JSON-RPC 2.0
поверх stdio, з рукостисканням `initialize`, `tools/list` та `tools/call`.
Жоден справжній MCP-клієнт (Claude Code, Cursor, …) не може спілкуватися з цим
сервером. Кореневий `mcp.json` також не у форматі, який читають поширені клієнти
(Claude Code очікує `.mcp.json` з об'єктом `mcpServers`). **Головна обіцянка
проєкту — "доступ для AI-агента через MCP" — сьогодні не працює.**
Виправлення: переписати з офіційним Python SDK `mcp` (FastMCP потребує ~20 рядків).

**C2 — Перший запит на свіжій машині падає І ламає кеш BM25.**
*(підтверджено відтворенням)*
Що відбувається у `scripts/query_index.py:50-58`: коли `bm25.pkl` не
існує, `get_bm25_retriever()` бере вузли з `index.docstore.docs` —
але це сховище **порожнє**, коли індекс завантажується з Qdrant
(`load_index()` ніколи його не заповнює). Код зберігає цей порожній список до
`bm25.pkl`, а потім `BM25Retriever.from_defaults(nodes=[])` викидає
`ValueError`. Після цього кожен наступний запит завантажує зламаний файл кешу і
падає так само, доки хтось не запустить `build_index.py` знову або не видалить
файл.
Виправлення: перевіряти список перед збереженням; падати з чітким повідомленням
("run build_index.py first").

**C3 — Кожен запит платить за повний холодний старт.**
`mcp_server.py:5-9` запускає новий процес `python query_index.py` на кожен запит.
Кожен запуск знову завантажує ~400 МБ модель ембедингів BGE, знову читає обидва
файли кешу і знову перепідключається до Qdrant. Один запит займає десятки секунд.
Внутрішньопроцесні кеші (`_retrieve_cache`, `_engine`) марні, бо процес помирає
після одного запиту. Затверджений дизайн сервісу існує саме для того, щоб це
виправити. Реалізуйте його.

**C4 — Крихкий старт процесу.**
`mcp_server.py:6` запускає `["python", ".claude/scripts/query_index.py", query]`.
Проблеми: `python` може бути відсутнім у PATH (Debian використовує `python3`), він
може вказувати на неправильний інтерпретатор (не на venv), а шлях до скрипта працює
лише тоді, коли поточний каталог є коренем розгорнутого проєкту. Використовуйте
`sys.executable` і шлях на основі `__file__`.

### Високі

**H1 — Математика злиття оцінок неправильна.**
`query_index.py:228-244` нормалізує **один змішаний список** оцінок за допомогою
min-max. Але оцінки приходять з різних шкал: косинусна подібність — приблизно
0–1, BM25 не має верхньої межі (часто >10). Одна висока оцінка BM25 стає
максимумом і притискає всі векторні оцінки близько до 0. Частина `(1-alpha)` у
формулі тоді майже не несе інформації. Стандартне виправлення: **Reciprocal Rank
Fusion (RRF)** — воно використовує лише ранги, а не сирі оцінки, і потребує ~5
рядків. Документ дизайну вже вказує це як відкладений пункт "R2".

**H2 — Кандидатів відсікають до ранжування.**
`query_index.py:205` залишає лише перші 30 унікальних вузлів у тому порядку, в
якому їх повернули ретривери (спершу вузький векторний, потім BM25, потім широкий
векторний, ×3 варіанти питання). Унікальні результати від пізніших ретриверів
тихо відкидаються до того, як крок ранжування може їх оцінити. Ранжувальник може
лише опускати елементи вниз — він ніколи не може врятувати відкинутий елемент.
Відсікайте *після* оцінювання або змішуйте списки чесно.

**H3 — Кеш ембедингів: росте вічно, повільні записи, немає перевірки моделі.**
`query_index.py:161-173` записує **весь** словник кешу на диск при кожному
промаху кешу (до 30 повних записів на запит), і кеш ніколи не зменшується.
Гірше: ключ кешу — лише текст. Якщо ви зміните модель ембедингів у
`model_setup.py`, старі вектори все одно використовуються — неправильний
векторний простір, можливо, неправильна розмірність. Виправлення: робіть ключем
кешу `(model_name, text)` або зберігайте ім'я моделі у файлі і відкидайте кеш при
розбіжності; записуйте на диск один раз на запит; обмежте розмір (LRU).

**H4 — Немає файлу залежностей, немає закріплення версій.**
Залежності існують лише як блок `pip install` у `README.md` та незакріплений
`eval/requirements-eval.txt`. Завдання 1 плану реалізації (кореневий
`requirements.txt` + `requirements-dev.txt`) ніколи не виконане. Збірки
невідтворювані — LlamaIndex часто ламає свій API між мінорними версіями.

**H5 — Сам конвеєр не має жодних тестів.**
Усі наявні тести покривають `eval/` (метрики + оркестрація). Немає тестів для
`query_index.py`, `build_index.py`, `qdrant.py`, `ask.py` чи
`mcp_server.py`, і немає CI, що щось запускає.

**H6 — Перебудова індексу спершу видаляє, потім будує.**
`build_index.py:74-95` видаляє наявну колекцію *перед* тим, як збудувати нову.
Якщо збірка падає посередині (брак пам'яті, Ctrl-C, проблема з Qdrant), у вас
**взагалі немає індексу**. Продакшен-патерн: будувати в нову колекцію, потім
перемкнути аліас Qdrant, а потім видалити стару.

**H7 — Жорстко закодована конфігурація скрізь; демо ділить продакшен-колекцію.**
`COLLECTION_NAME = "demo"`, `localhost:6333` (`qdrant.py:7-10`), імена моделей
(`model_setup.py`) і — найгірше — припущення про домен усередині узагальненого
конвеєра: `expand_query()` додає `".NET core backend"` до кожного запиту
(`query_index.py:137-142`). Оскільки демо для оцінювання і реальне розгортання
використовують ту саму назву колекції `"demo"`, `eval/run_demo.sh` **видаляє ваш
реальний індекс** (сам скрипт попереджає про це). Усе це потребує шару
середовища/конфігурації.

### Середні

- **M1 — Важка робота під час імпорту.** `query_index.py` запускає
  `cache_warmup()` при імпорті (рядок 48); імпорт `model_setup` завантажує
  HF-модель і змінює глобальні `Settings`. Саме тому `tests/conftest.py`
  мусить підміняти `model_setup` фейком. Перенесіть цю роботу в явні функції
  ініціалізації.
- **M2 — Pickle як формат сховища.** `pickle.load` для `bm25.pkl` /
  `embeddings.pkl` виконує довільний код, якщо файл змінили. Крім того,
  сам документ дизайну каже, що вузли LlamaIndex не серіалізуються через
  pickle надійно. Затверджений дизайн (BM25, перебудований з Qdrant, у
  пам'яті) усуває найгірший випадок.
- **M3 — Слабка перевірка якості відповіді в `ask.py`.** Рядки 50-61 вирішують,
  що відповідь погана, шукаючи фрази на кшталт "not enough information". Це
  залежить від моделі і тихо помиляється в обидва боки. Також
  `MAX_CONTEXT_CHARS = 6000` (~1.5k токенів) дуже мало для питань про код.
- **M4 — `ask.py` змішує логи у stdout.** `DEBUG = True` друкує
  `[DEBUG] Mode: ...` у stdout поруч із відповіддю (на відміну від
  `query_index.py`, який надсилає логи до stderr).
- **M5 — Інтерактивний `input()` у `build_index.py:56-59`** блокує всю
  автоматизацію; `run_demo.sh` обходить це через `echo y`. Додайте `--force`.
- **M6 — Немає інкрементного індексування.** Будь-яка зміна у джерелі означає
  повторне обчислення ембедингів для всього репозиторію.
- **M7 — `_retrieve_cache` росте без обмежень** і марний у поточній моделі
  "процес-на-запит" (він помирає разом із процесом).
- **M8 — `SentenceSplitter` на коді C#.** Текстовий розбивач ріже методи
  посередині і відокремлює сигнатури від тіл. Розбиття на фрагменти з
  урахуванням коду (AST / tree-sitter) — найбільший очікуваний виграш у
  якості, і середовище оцінювання може це виміряти.
- **M9 — Зламані посилання в документації.** `eval/README.md`, `run_eval.py` та
  `run_demo.sh` усі вказують на "TODO.md §0", але жодного `TODO.md` у
  репозиторії немає (лише `TODO.Instruction.md`, який є настановою для агента).
  Документ дорожньої карти втрачено; документи дизайну/плану в
  `docs/superpowers/` покривають його частину.
- **M10 — Qdrant працює без автентифікації**, а `ensure_qdrant()` викликає
  Docker CLI, який не може працювати зсередини контейнера (документ дизайну
  виправляє це перемикачем `QDRANT_AUTOSTART` через env).
- **M11 — Дрібні косметичні пункти:** український коментар у `qdrant.py:43`,
  одруківки ("Termanated", "Are you wanna"), логування на основі `print` із
  заміненою вбудованою функцією замість модуля `logging`.

## 4. Загальний висновок

Поділ на стадії (індексування / пошук / відповідь / обслуговування) правильний, а
рецепт пошуку (щільний + BM25 + переранжування) — слушна форма гібридного пошуку.
Проблеми сидять у з'єднаннях між частинами: час життя процесу (холодний старт на
кожен запит), сховище (pickle), протокол (не справжній MCP) і
конфігурація (жорстко закодовані значення). Важливо: команда вже зрозуміла
більшість із цього — документ дизайну від 2026-06-01 дає правильні ліки.
**Найважливіший висновок цього огляду: наступний крок — не проєктувати щось
нове. Це збудувати дизайн, який уже затверджено**, плюс замінити шар MCP
справжнім протоколом (старий дизайн не покривав цю частину — його
`mcp_server.py` зберігає той самий фейковий рядковий протокол і лише змінює
підпроцес на HTTP).

Дивіться `2026-06-11-production-readiness-plan.md` (той самий каталог) для
впорядкованого плану робіт, а `/handoff.md` для живого статусу проєкту.
