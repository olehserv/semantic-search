# Тривало працюючий сервіс пошуку — Дизайн

**Дата:** 2026-06-01
**Статус:** ✅ Реалізовано 2026-06-12 (гілка `phase-1-search-service`), з
однією зміною: `mcp_server.py` став справжнім MCP-сервером (офіційний SDK `mcp`,
FastMCP/stdio) замість збереження рядкового протоколу. Стек контейнерів перевірено
через docker compose 2026-06-13 (повний рантайм-чекліст нижче пройдено).

## Контекст

Сьогодні кожен пошук запускає `query_index.py` як **новий процес на запит**
(стартований `mcp_server.py`). Дві проблеми спонукають до цієї зміни:

1. **Кешування BM25 через pickle ненадійне.** Виправлення B2 зберігало
   розібрані вузли до `bm25.pkl`, тож кожен новий процес міг перебудувати BM25.
   Але серіалізація вузлів LlamaIndex через pickle не відновлює їх чисто. Ми
   хочемо прибрати файл pickle і тримати BM25 **лише в пам'яті**.
2. **Усе перебудовується для кожного запиту.** Кожен процес знову завантажує
   індекс, модель ембедингів і ретривер BM25. BM25 у пам'яті працює лише
   тоді, коли процес **живе довго**: збудувати ретривери один раз, тримати їх
   прогрітими, повторно використовувати для кожного запиту.

Результат: **сервіс пошуку**, який працює весь час (у Docker) і тримає
прогрітий рушій, плюс тонкий MCP-шим, що пересилає запити до нього через HTTP.

## Рішення

- **Інтерфейс:** HTTP-сервіс (Flask) + тонкий MCP-шим. `mcp_server.py`
  пересилає до сервісу замість запуску процесу.
- **Обчислення:** автовизначення — `device = "cuda" if torch.cuda.is_available() else "cpu"`.
- **Індексування:** не частина сервісу. `build_index.py` лишається окремим,
  ручним кроком індексування; сервіс очікує, що Qdrant уже заповнено.
- **Джерело вузлів BM25:** перебудувати вузли з **колекції Qdrant на
  старті**. Це зберігає оригінальні ID вузлів, тож дедуплікація проти
  векторного ретривера все ще працює. Дерево джерела в контейнері не потрібне,
  і немає pickle.
- **LLM:** сервіс **не** використовує Ollama. `search_codebase` → `query()`
  — це лише пошук + ембединги. `ask.py` (який використовує LLM) лишається
  окремим CLI. Немає endpoint `/ask` (YAGNI).
- **Веб-фреймворк:** Flask (один endpoint із прогрітим singleton'ом; одна
  залежність).

## Архітектура

```
build_index.py  ──(offline, manual)──>  Qdrant   (vectors + payload)
                                           │
search-service (container, always up)      │ scroll at startup
  startup: model_setup (auto device)       ▼
           load_index(from_vector_store) + rebuild nodes from Qdrant
           → build vector(top6) + bm25(in-mem) + wide(top12) → warm singleton
  POST /search {"query": "..."} ──> query() on warm engine ──> JSON
  GET  /health

agent ──starts──> mcp_server.py (shim) ──HTTP POST /search──> search-service
```

## Компоненти і зміни

### `query_index.py`
- **Прибрати** весь pickle-код BM25: константу `BM25_CACHE_PATH`, глобальну
  `bm25_retriever_nodes_cache`, частину BM25 у `cache_warmup()`,
  і pickle-читання/запис усередині `get_bm25_retriever()`.
- **Додати** завантажувач вузлів, який перебудовує всі вузли з Qdrant: scroll по
  колекції і перебудова кожного вузла через
  `llama_index.core.vector_stores.utils.metadata_dict_to_node(payload, text=payload.get("text"))`;
  якщо це не вдається, відкат до простого
  `TextNode(id_=point.id, text=payload["text"], metadata=...)`.
  `get_bm25_retriever()` тоді будує
  `BM25Retriever.from_defaults(nodes=<rebuilt nodes>)` у пам'яті.
- Наявний singleton `_engine` (`get_engine()`) лишається як є. Це
  те, що тримає три ретривери прогрітими між запитами в довгоживучому
  процесі.
- Pickle кешу ембедингів (`EMB_CACHE_PATH`) **лишається**, з атомарним
  записом R3.

### `build_index.py`
- **Прибрати** pickle-запис вузлів з B2 (і константу `BM25_CACHE_PATH` /
  імпорт `pickle`, якщо потім невикористовуваний). Виправлення B4/B5 лишаються.

### `service.py` *(новий)*
- Застосунок Flask. На старті: імпортувати `model_setup`, викликати `get_engine()`,
  щоб прогріти ретривери, залогувати, що він готовий.
- `POST /search` — тіло `{"query": "..."}`; повертає JSON з `query()`.
  Повертає JSON-помилку у стилі 400 для відсутнього/порожнього запиту, і
  JSON-помилку у стилі 500 при збої.
- `GET /health` — повертає `{"status": "ok"}`, щойно рушій прогрітий.
- Працює на вбудованому сервері Flask (один воркер, тож прогрітий singleton
  спільний) на `0.0.0.0:8000`.

### `mcp_server.py`
- Замінити `subprocess.run([...query_index.py...])` на HTTP `POST` до
  `f"{SEARCH_SERVICE_URL}/search"` (`SEARCH_SERVICE_URL` з env, за замовчуванням
  `http://localhost:8000`).
- Зберегти стійкість B6/B7: зупинятися на EOF, структурована помилка для
  поганого JSON, явна помилка "unknown tool" і структурована помилка, коли
  сервіс недосяжний або повертає не-200.

### `qdrant.py`
- `QDRANT_HOST = os.getenv("QDRANT_HOST", "localhost")` (і опційно
  `QDRANT_PORT` з env), щоб контейнер міг дістатися до compose-сервісу
  `qdrant`.
- `ensure_qdrant()` отримує env-перемикач `QDRANT_AUTOSTART` (за замовчуванням `"1"`).
  Коли він `"0"` (заданий усередині контейнера), функція **чекає і
  повторює спроби**, доки Qdrant не стане досяжним, і кидає чітку помилку, якщо
  він так і не стане — замість спроби запустити `docker` (що неможливо
  всередині контейнера).

### `model_setup.py`
- `device = "cuda" if torch.cuda.is_available() else "cpu"` (імпортувати `torch`).
  Зберігає конфігурацію LLM Ollama для `ask.py`.

### `Dockerfile` *(новий)* + `requirements.txt` *(новий)* + `docker-compose.yml`
- `requirements.txt`: закріпити рантайм-залежності (llama-index core + qdrant +
  huggingface embeddings + bm25 retriever, `qdrant-client`, `torch`,
  `numpy`, `requests`, `flask`). CPU-torch wheel за замовчуванням.
- `Dockerfile`: базовий образ Python (CPU підходить), встановити `requirements.txt`,
  скопіювати скрипти, `CMD` запускає `service.py`. GPU — опціональне ввімкнення
  (перемкнутися на базовий образ CUDA; код автовизначення використовує GPU,
  коли хост його надає).
- `docker-compose.yml`: додати `search-service` (збірка з Dockerfile),
  `depends_on: [qdrant]`, порти `8000:8000`, env `QDRANT_HOST=qdrant`,
  `QDRANT_AUTOSTART=0`, і том для кешу моделі HuggingFace, щоб
  модель ембедингів не завантажувалася при кожному старті. Резервування GPU
  задокументоване як опціональний блок `deploy.resources`.

## Потік даних (один запит)

1. (офлайн) `build_index.py` заповнює колекцію Qdrant.
2. `search-service` стартує: налаштовує модель ембедингів (авто-пристрій),
   підключається до Qdrant (чекає/повторює), перебудовує вузли з Qdrant, будує
   векторний/BM25/широкий ретривери і тримає їх як прогрітий singleton `_engine`.
3. Агент стартує `mcp_server.py`; він читає запит `search_codebase`
   зі stdin і `POST`ить запит до сервісу.
4. Сервіс запускає `query()` на прогрітому рушії і повертає ранжовані сніпети
   як JSON; шим передає його назад агентові.

## Обробка помилок

- **Старт сервісу:** якщо Qdrant так і не стає досяжним, залогувати чітку помилку
  і вийти з ненульовим кодом (compose `depends_on` + цикл повтору покривають
  порядок старту).
- **/search:** відсутній/порожній `query` → JSON-помилка; виняток усередині
  `query()` → JSON-помилка з повідомленням (також залогована на сервері).
- **MCP-шим:** сервіс недоступний / не-200 / поганий JSON → структурована
  відповідь `{"error": ...}` (вона ніколи не вішає агента); EOF і невідомі
  інструменти обробляються як сьогодні.

## Тестування / верифікація

- **Статично (тут):** `python -m py_compile scripts/*.py service.py`.
- **Юніт-тест шима (тут):** прогнати `mcp_server.py` через stdin із
  `SEARCH_SERVICE_URL`, що вказує на закритий порт, і перевірити, що він повертає
  структуровану помилку (без додаткових залежностей), плюс наявні випадки поганого
  JSON / невідомого інструменту.
- **Рантайм (машина користувача):**
  1. `docker compose up -d qdrant`; запустити `build_index.py`, щоб заповнити колекцію.
  2. `docker compose up -d search-service`; `curl localhost:8000/health` → `ok`.
  3. `curl -XPOST localhost:8000/search -d '{"query":"where is auth handled"}'`
     повертає ранжований JSON, і **з'являються попадання лише за ключовими словами BM25**
     (це доводить, що BM25 збудовано з Qdrant, у пам'яті).
  4. Прогнати `mcp_server.py` (із піднятим сервісом) і перевірити на валідний JSON-
     результат.
  5. Перевірити, що модель ембедингів завантажується лише раз (закешована у
     томі), і що рушій будується один раз на старті, а не на кожен запит.

## Поза обсягом (відкладено)

- R2 (нормалізація змішаних шкал оцінок), R4 (кеші без обмежень розміру — ще
  менш важливе з одним прогрітим процесом), R5 (повторне обчислення ембедингів).
- Endpoint `/ask` (LLM) у сервісі.
- Автоматична побудова/оновлення індексу всередині сервісу.
