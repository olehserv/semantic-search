# Оцінювання якості пошуку

Ця тека вимірює, наскільки добрий пошук. Правило для проєкту:
**зміна пошуку є покращенням лише тоді, коли ці числа стають кращими.**
Кожне завдання Phase 2 у `docs/reviews/2026-06-11-production-readiness-plan.md`
(RRF-злиття, розбиття на фрагменти з урахуванням коду, переранжувальник, …) має
бути перевірене тут перед тим, як його буде злито.

Як це працює: для кожного питання в розміченому "еталонному наборі" середовище
запускає реальний конвеєр `query()`. Воно дивиться, з яких **файлів** прийшли
результати, і порівнює їх із файлами, які відомі як правильні.

| Метрика | Що вона вам каже |
|--------|-------------------|
| **Recall@k** | Зі скількох правильних файлів скільки потрапили в топ-k результатів? |
| **MRR** | Наскільки високо перший правильний файл? (1.0 = завжди на ранзі 1) |
| **nDCG@k** | Чи правильні файли близько до верху? Нижчі позиції отримують менше заслуги. |

| Файл | Роль |
|------|------|
| `metrics.py` | Метричні функції (лише stdlib, з юніт-тестами) |
| `run_eval.py` | Запускає `query()` для кожного еталонного питання і друкує звіт |
| `golden.jsonl` | Розмічений набір: один `{"query", "relevant_files"}` на рядок |
| `golden_real.jsonl` | 40 питань для реального проєкту в `sample_real/` (див. нижче) |
| `sample_corpus/` | Маленький фейковий застосунок .NET, щоб демо працювало самостійно |
| `sample_real/` | Реальний проєкт .NET (LookingForMentor) для чесних чисел — постачається з репозиторієм |
| `baselines/` | Записані звіти оцінювання; зміни Phase 2 мають перевершувати ці числа |
| `run_demo.sh` | Одна команда: venv + Qdrant + індексування корпусу + запуск оцінювання |

## Запуск

```bash
bash eval/run_demo.sh            # full demo on the sample corpus
python3 -m pytest tests/ -q     # unit tests (no Docker or ML stack needed)
```

**Попередження:** демо перебудовує колекцію Qdrant, названу в
`scripts/qdrant.py` (`COLLECTION_NAME`). Якщо ваш реальний індекс використовує ту
саму назву, демо його замінить. Назва задається через env
(`QDRANT_COLLECTION`, за замовчуванням `demo`), тож давайте реальним індексам
власну колекцію.

## Запуск у CI (вручну)

Існує ручне завдання GitHub Actions, `.github/workflows/eval.yml` (тригер:
"Run workflow" / `workflow_dispatch`). Воно встановлює повний ML-стек, запускає
сервісний контейнер Qdrant, індексує **зразковий корпус**, запускає оцінювання і
**падає, якщо будь-яка метрика опускається нижче** збереженого базового рівня
зразка (`baselines/2026-06-13-sample-chunking.json`, який дорівнює 1.000 на всьому).
Звіт завантажується як артефакт `eval-report`. Воно ручне навмисно: воно
завантажує CPU-torch і модель ембедингів, тож воно надто важке для кожного push
(швидкий `ci.yml` лишається без ML).

## Ручки налаштування (env-змінні)

| Env-змінна | За замовчуванням | Ефект |
|---------|---------|--------|
| `QUERY_VARIANT_SUFFIXES` | `implementation` | Додаткові варіанти запиту; задавайте підказки домену тут (див. нижче). |
| `RERANK_CANDIDATES` | `30` | Скільки топ-злитих кандидатів йдуть на переранжування ембедингами. Лише під час запиту — без переіндексування, щоб це змінити. |
| `CROSS_ENCODER_MODEL` | _(порожнє = вимкнено)_ | Задайте ім'я cross-encoder'а, щоб переранжувати ним замість косинусної суміші. Рекомендовано: `cross-encoder/ms-marco-MiniLM-L-6-v2`. |

`RERANK_CANDIDATES` було додано, щоб виміряти завдання 2.2 (чи шкодить
recall відсікання після злиття?). На реальному проєкті відповідь — **ні**: пул
кандидатів на запит лише ~16–23, завжди менший за 30, тож кожне значення від 30
аж до "без відсікання" дає ті самі числа (Recall@5 0.912 / MRR 0.716 / nDCG@5 0.760).
Ручка лишається для майбутнього налаштування, якщо ретривери колись розширять.

`CROSS_ENCODER_MODEL` (завдання 2.6) вмикає опціональний cross-encoder-переранжувальник,
змішаний з оцінкою RRF. Він **вимкнений за замовчуванням**, бо обмінює затримку
на скромний виграш у якості. Виміряно на реальному проєкті:

| Переранжувальник | Recall@5 | MRR | nDCG@5 | Затримка CPU / запит |
|-----------|---------:|----:|-------:|--------------------:|
| cosine + RRF (за замовчуванням) | 0.912 | 0.716 | 0.760 | ~0.16 s |
| `ms-marco-MiniLM-L-6-v2` + RRF | 0.925 | **0.751** | **0.782** | ~1.0 s |
| `BAAI/bge-reranker-base` + RRF | **0.938** | 0.747 | 0.786 | ~5.9 s |

MiniLM-L6 — золота середина (найкращий MRR, ~90 МБ, ~1 с на CPU). Cross-encoder
**змішується, а не використовується сам по собі** — чисте впорядкування
cross-encoder'ом отримало оцінку *гіршу* за замовчування (0.875 / 0.686 / 0.721),
бо воно відкидає сигнал BM25/ключових слів, на який покладається пошук по коду.
Звіт із увімкненим MiniLM збережено як
`baselines/2026-06-13-real-cross-encoder.json`.

## Базовий рівень реального проєкту

`golden_real.jsonl` містить 40 питань про проєкт LookingForMentor
(застосунок .NET CQRS + Blazor у `sample_real/`, частина репозиторію). Мітки
використовують імена файлів, що існують рівно один раз у цьому проєкті
(`ErrorHandlingMiddleware.cs` існує двічі, але обидві копії — правильні
відповіді). Щоб відтворити базовий рівень:

```bash
cd eval/sample_real/LookingForMentor-main
QDRANT_COLLECTION=lfm PYTHONPATH=../../../scripts \
  ../../../.venv/bin/python ../../../scripts/build_index.py --force
QUERY_VARIANT_SUFFIXES="implementation,.NET core backend" \
  QDRANT_COLLECTION=lfm PYTHONPATH=../../../scripts:../../../eval \
  ../../../.venv/bin/python ../../../eval/run_eval.py \
  --golden ../../../eval/golden_real.jsonl --k 5 \
  --out ../../../eval/baselines/<date>-real.json
```

Записані числа використовують суфікс варіанту `.NET core backend` — це підказка
домену, яка вимірювано допомагає на цьому корпусі .NET (без неї:
Recall@5 0.738 проти 0.787). Тримайте його заданим при порівнянні з
базовими рівнями, інакше порівняння нечесне.

## Використання на власному проєкті

1. Проіндексуйте свою кодову базу (див. README верхнього рівня).
2. Замініть `golden.jsonl` на **30–50** питань, які люди справді ставлять
   про ваш код. Для кожного питання напишіть файл(и), що на нього відповідають.
   Мішайте різні типи: "де є X", "як працює Y", точні пошуки за іменами
   і концептуальні питання. Хороші мітки важать більше, ніж багато міток.
3. ```bash
   PYTHONPATH=scripts:eval python eval/run_eval.py --golden eval/golden.jsonl --k 5 --out report.json
   ```
4. Запишіть числа. Змініть **одну** річ у пошуку. Запустіть знову.
   Залиште зміну лише тоді, коли числа зростуть.

### Формат еталонного файлу

```json
{"query": "where is authentication handled", "relevant_files": ["AuthService.cs"]}
{"query": "what happens when an order is placed", "relevant_files": ["OrdersController.cs", "EmailService.cs"]}
```

`relevant_files` — це *імена* файлів (без шляху). Одне питання може мати
кілька правильних файлів.
